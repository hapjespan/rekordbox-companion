## Problem, in one paragraph

A working DJ receives song requests and reference lists as Spotify playlists,
but performs from a personal, carefully curated local library managed in
Rekordbox. There is no fast way to know which requested tracks the library
already holds, to turn that knowledge into a performance-ready playlist, to see
what is missing and buy it, or to slice the library into structures that fit a
booking. Preparing one booking costs hours; the library itself is irreplaceable
and must never be put at risk by the tool that saves that time.

## Decision log delta

D1 to D4 were resolved at kickoff and stand unchanged (see `specs/kickoff.md`
section 13 and ADRs 0002 to 0005). Phase 1 added:

- D5: Re-sync updates the companion-created playlist, add-only. ADR 0006.
- D6: Reject means "not the right track" and routes the track to the missing
  queue; "do not want" is expressed as ignoring the missing track. Glossary.
- D7: Genres are enriched externally, stored app-side with manual override,
  never written to Rekordbox. Hard v1 dependency. ADR 0007.
- D8: Booking structures are hand-designed; the app contributes ranked, filtered
  suggestions per playlist. Auto-generated taxonomies are out. Structure
  templates are deferred (parking lot). ADR 0008.
- D9: Embedded full-track Spotify playback in the review UI via the Web
  Playback SDK, backed by the owner's Premium account. ADR 0009.
- D10: Input logistics. Delivered: design token set (in `web/design-input/`).
  Still owed by the owner before the implementation phase: a fixture copy of
  `master.db`, a Spotify Developer client id, confirmation that the SQLCipher
  key was obtained on the Mac (`python -m pyrekordbox download-key`).

## Scope corrections relative to the kickoff document

1. Kickoff section 10 phase 4 describes a structure generator that proposes a
   taxonomy; D8 replaces it with hand-designed structures plus suggestions.
2. Kickoff section 7's `structure_proposal` model and section 8's
   `/api/structure/proposals` endpoints reflect the old generator idea and will
   be reshaped in phase 2/4.
3. Genre enrichment (D7) is new scope that kickoff did not contain; it is
   load-bearing for the booking feature and needs its own stories, data model
   and external-source decision.
4. Embedded Spotify playback (D9) replaces kickoff's implicit local-only preview
   during review, and adds OAuth scopes and a Premium dependency.
5. Re-sync semantics (D5) refine kickoff's single `apply` action into
   create-or-update with add-only writes.

## The three biggest unknowns

Each becomes a constraint or a risk in phase 3, never a surprise in phase 6.

1. Write compatibility of pyrekordbox with Rekordbox 7.2.17: can it create
   playlists and folders that Rekordbox reads back flawlessly, including the
   add-only update path? Answered by: engineering, smoke test against the
   fixture master.db, final verification on the owner's Mac.
2. Genre enrichment coverage and quality: do Spotify artist genres plus an open
   music database cover a 10k+ mp3/m4a library well enough to drive
   suggestions? Answered by: engineering spike on the fixture collection, with
   the owner judging a sample for correctness.
3. Spotify Web Playback SDK on localhost: does full-track playback (DRM/EME)
   work in the owner's browser against a 127.0.0.1 app with a PKCE token?
   Answered by: engineering spike in an early implementation phase.

Minor open item carried from kickoff: verify the ISRC fill rate on the real
database with one query (owner's Mac, non-blocking).
